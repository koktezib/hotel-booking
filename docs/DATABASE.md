# База данных

У Booking и Hotel отдельные базы H2 в памяти. Сервисы обмениваются данными через API и не обращаются к чужим таблицам. Eureka и Gateway своих баз не имеют.

Таблицы создаёт Hibernate по JPA-сущностям. В настройках стоит `ddl-auto=create-drop`, поэтому данные не сохраняются после остановки сервиса.

## Booking Service

В этой базе две таблицы: `users` и `bookings`. У одного пользователя может быть несколько бронирований.

### users

| Поле | Назначение |
|---|---|
| `id` | Первичный ключ, числовой идентификатор пользователя |
| `username` | Уникальный логин, до 50 символов |
| `password` | BCrypt-хеш пароля |
| `role` | Роль USER или ADMIN |
| `enabled` | Активен ли аккаунт |

Все поля обязательные. При удалении пользователя выставляется `enabled=false`: запись остаётся, чтобы не потерять связь с историей бронирований. Перед этим нужно отменить его активные брони. Имя отключённого пользователя остаётся занятым, повторно зарегистрировать его нельзя.

### bookings

| Поле | Назначение |
|---|---|
| `id` | Первичный ключ UUID, идентификатор брони |
| `user_id` | Внешний ключ на `users.id` |
| `request_id` | UUID запроса клиента, нужен для обработки повторов |
| `room_id` | Идентификатор выбранного номера |
| `hotel_id` | Необязательный фильтр отеля для автоподбора |
| `auto_select` | Нужно ли подобрать номер автоматически |
| `start_date`, `end_date` | Даты заезда и выезда |
| `status` | PENDING, CONFIRMED или CANCELLED |
| `created_at`, `updated_at` | Время создания и последнего изменения |
| `release_pending` | Нужно ли ещё освободить номер в Hotel |
| `failure_status` | HTTP-код ошибки, если создание брони не удалось |
| `failure_reason` | Причина ошибки или отмены, до 500 символов |
| `trace_id` | Идентификатор для поиска связанных логов, до 64 символов |
| `version` | Версия записи для проверки конкурентных изменений через `@Version` |

`room_id` может быть пустым, если номер ещё не выбран. `hotel_id`, `failure_status` и `failure_reason` также могут быть NULL. У `room_id` нет внешнего ключа на таблицу номеров: она находится в базе другого сервиса. При ручном выборе используется `room_id`; фильтр `hotel_id` применяется при автоподборе.

Пара `(user_id, request_id)` уникальна. Один пользователь не может создать две записи с одним ключом запроса, но разные пользователи могут использовать одинаковый `requestId`. При создании брони строка пользователя блокируется, чтобы параллельные повторы не вставили две записи.

Дополнительные индексы:

- `idx_booking_owner (user_id, created_at)` — для истории пользователя;
- `idx_booking_recovery (status, release_pending, created_at)` — для поиска записей, которым нужна отмена или повторное освобождение номера.

## Hotel Service

Здесь находятся `hotels`, `rooms` и своя таблица `bookings`. Последняя хранит занятые периоды номеров. Её имя совпадает с таблицей Booking Service, но это разные таблицы в разных базах.

### hotels

| Поле | Назначение |
|---|---|
| `id` | Первичный ключ, числовой идентификатор отеля |
| `name` | Название, до 120 символов |
| `address` | Адрес, до 250 символов |

Все поля обязательные. Удалить отель можно после удаления его номеров.

### rooms

| Поле | Назначение |
|---|---|
| `id` | Первичный ключ, числовой идентификатор номера |
| `hotel_id` | Внешний ключ на `hotels.id` |
| `number` | Номер комнаты, до 30 символов |
| `available` | Можно ли заселять гостей в этот номер |
| `times_booked` | Количество подтверждённых и не отменённых броней |
| `version` | Версия записи для `@Version` |

Пара `(hotel_id, number)` уникальна: в одном отеле не может быть двух комнат с одинаковым номером. Индекс `idx_room_rank (available, times_booked, id)` создан для отбора доступных номеров и сортировки по загрузке.

`available=false` используется, например, для ремонта. Занятость по датам проверяется отдельно. Изменение этого флага не отменяет уже существующие брони.

Номер с историей бронирований нельзя удалить физически. Его можно вывести из эксплуатации через `available=false`.

### bookings

В коде этой таблице соответствует сущность `Reservation`.

| Поле | Назначение |
|---|---|
| `id` | Первичный ключ UUID, тот же `bookingId`, что в Booking Service |
| `room_id` | Внешний ключ на `rooms.id` |
| `start_date`, `end_date` | Занятый период |
| `released` | Освобождён ли номер по этой брони |
| `created_at` | Время создания записи |

Для поиска пересечений есть индекс `idx_slot_overlap (room_id, released, start_date, end_date)`.

Две брони пересекаются, если начало существующей брони раньше нового выезда, а её окончание позже нового заезда:

```sql
released = false
AND start_date < :requestedEnd
AND end_date > :requestedStart
```

День выезда не считается занятым. Например, проживание с 10-го по 12-е не мешает следующему гостю заехать 12-го.

Проверка пересечения, запись периода и изменение `times_booked` выполняются в одной транзакции с блокировкой строки номера. Это защищает от двух одновременных бронирований на одни даты. Повторное подтверждение того же `bookingId` с теми же данными ничего не меняет.

Если освобождение пришло раньше подтверждения, сохраняется запись с `released=true` и пустыми датами. Это отметка отмены, или tombstone. Позднее подтверждение с тем же id получит `409`. Такие отметки хранятся до остановки базы, а повторное освобождение проходит без дополнительных изменений.

## Статистика

`times_booked` увеличивается при подтверждении и уменьшается при отмене. Прошедшие проживания остаются в счётчике. Повторы запросов его не увеличивают.

Для статистики за период считаются занятые ночи. Если бронь выходит за границы выбранного периода, учитываются только ночи внутри него. Процент занятости номера — число занятых ночей, делённое на длительность периода, умноженное на 100.

Общий процент считается по всем номерам выбранного отеля, включая номера на ремонте. Число номеров, пригодных для заселения, возвращается отдельно в `operationalRooms`.
