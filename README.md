# Бронирование отелей

REST API для бронирования номеров. Пользователь может посмотреть отели, выбрать номер, создать бронь и отменить её. Администратор управляет отелями, номерами и пользователями, а также смотрит статистику занятости.

Проект состоит из четырёх Spring Boot приложений. Отдельного сайта нет, запросы можно отправлять через Swagger или API Gateway.

## Что используется

Java 17+, Spring Boot 3.5.16, Spring Cloud 2025.0.3, Spring Data JPA, H2, Spring Security и JWT. Для обработки сбоев используется Resilience4j, для документации API — Swagger/OpenAPI. Сборка через Maven Wrapper, тесты — JUnit, MockMvc и WebTestClient.

## Как устроен проект

| Модуль | За что отвечает | Порт |
|---|---|---|
| `discovery-server` | Eureka: хранит адреса запущенных сервисов | 8761 |
| `api-gateway` | Принимает запросы, проверяет JWT и направляет их в нужный сервис | 8080 |
| `booking-service` | Пользователи, вход и регистрация, создание и отмена бронирований | 8082 |
| `hotel-service` | Отели, номера, проверка свободных дат и статистика | 8081 |

В модуле `common` лежат общие DTO, обработка ошибок и настройки безопасности. Самостоятельно он не запускается.

```text
Клиент → Gateway → Booking Service → H2 пользователей и броней
            │             │
            │             └── подтверждение / освобождение номера
            ↓                              ↓
        Hotel Service ←────────────────────┘
            ↓
        H2 отелей, номеров и занятых дат

Gateway, Booking и Hotel регистрируются в Eureka.
Gateway и Booking получают через неё адрес Hotel Service.
Gateway также получает адрес Booking Service.
```

Между Booking и Hotel используются HTTP-запросы. Каждый сервис работает только со своей базой.

## Запуск

Нужен JDK 17 или новее. Maven отдельно устанавливать не нужно: в проекте есть `mvnw` и `mvnw.cmd`. При первой сборке потребуется интернет для загрузки зависимостей.

В IntelliJ нужно открыть корневой `pom.xml` как Maven-проект и дождаться загрузки зависимостей. В проекте уже сохранены конфигурации `Eureka`, `Hotel`, `Booking`, `Gateway` и общая `Hotel Booking - All`.

Можно запустить общую конфигурацию или сначала Eureka, а затем остальные сервисы. В локальных настройках IDEA выбран JDK 21; при запуске на другом компьютере нужно выбрать установленный JDK в Project SDK. Для Hotel и Booking уже добавлен аргумент `--demo.enabled=true`, который создаёт тестовые данные.

JWT подписывается общим ключом. Для Gateway, Booking и Hotel нужно задать одинаковую переменную окружения `JWT_SECRET` длиной не меньше 32 байт. В IntelliJ это поле **Environment variables** в конфигурации запуска. Файл `.env` Spring Boot сам не загружает. Без переменной используется локальный демонстрационный ключ из настроек.

Сборка и тесты из терминала Windows:

```powershell
.\mvnw.cmd clean verify
```

На Linux/macOS команда — `./mvnw clean verify`. Переменная `JAVA_HOME` должна указывать на установленный JDK.

После сборки сервисы также можно запускать вручную. Каждая команда выполняется в отдельном терминале из корня проекта:

```text
java -jar discovery-server/target/discovery-server-1.0.0.jar
java -jar hotel-service/target/hotel-service-1.0.0.jar --demo.enabled=true
java -jar booking-service/target/booking-service-1.0.0.jar --demo.enabled=true
java -jar api-gateway/target/api-gateway-1.0.0.jar
```

Сервисы появляются в Eureka не сразу. Если Gateway в начале отвечает `503`, стоит проверить регистрацию сервисов и повторить запрос через некоторое время.

| Что открыть | Адрес |
|---|---|
| Gateway | http://localhost:8080 |
| Eureka | http://localhost:8761 |
| Swagger отелей и номеров | http://localhost:8081/swagger-ui/index.html |
| Swagger пользователей и бронирований | http://localhost:8082/swagger-ui/index.html |

Swagger отправляет запросы напрямую в свой сервис. Чтобы проверить маршрутизацию через Gateway, нужно отправлять запросы на порт `8080`. Состояние каждого приложения можно проверить по `/actuator/health`.

## Тестовые данные

При `demo.enabled=true` создаются два отеля, семь доступных номеров, один номер на ремонте и три пользователя:

| Логин | Пароль | Роль |
|---|---|---|
| `admin` | `Admin123!` | ADMIN |
| `alice` | `Alice123!` | USER |
| `bob` | `Bob12345!` | USER |

Для запросов в Swagger сначала нужно выполнить вход, скопировать `accessToken` из ответа и вставить его в поле **Authorize**. Токен действует один час.

H2 хранит данные в памяти. После остановки сервиса его база пропадает, а при следующем запуске с включённым заполнением тестовые данные создаются заново.

## Пример бронирования

Следующие команды PowerShell выполняют вход, автоматически выбирают номер и создают бронь:

```powershell
$login = Invoke-RestMethod http://localhost:8080/api/auth/login -Method Post -ContentType application/json -Body '{"username":"alice","password":"Alice123!"}'
$headers = @{ Authorization = "Bearer $($login.accessToken)" }
$body = @{
    requestId = [guid]::NewGuid().ToString()
    hotelId = 1
    autoSelect = $true
    startDate = [DateTime]::UtcNow.Date.AddDays(7).ToString('yyyy-MM-dd')
    endDate = [DateTime]::UtcNow.Date.AddDays(10).ToString('yyyy-MM-dd')
} | ConvertTo-Json
$booking = Invoke-RestMethod http://localhost:8080/api/bookings -Method Post -Headers $headers -ContentType application/json -Body $body
$booking
```

Посмотреть историю и отменить созданную бронь:

```powershell
Invoke-RestMethod http://localhost:8080/api/bookings -Headers $headers
Invoke-RestMethod "http://localhost:8080/api/bookings/$($booking.id)" -Method Delete -Headers $headers
```

Если отправить тот же запрос с прежним `requestId`, новая бронь не появится. Для новой операции нужен новый идентификатор. Если первый запрос ещё выполняется, повтор может вернуть `202 PENDING`; состояние можно проверить по адресу из заголовка `Location`.

## Основные запросы

| Метод и путь | Что делает |
|---|---|
| POST `/api/auth/register` | Регистрирует пользователя с ролью USER |
| POST `/api/auth/login` | Возвращает JWT после проверки логина и пароля |
| POST `/api/bookings` | Создаёт бронь с выбранным номером или автоподбором |
| GET `/api/bookings` | Возвращает историю текущего пользователя |
| GET / DELETE `/api/bookings/{id}` | Показывает или отменяет свою бронь |
| GET / POST `/api/users` | Список и создание пользователей, только ADMIN |
| GET / PATCH / DELETE `/api/users/{id}` | Просмотр, изменение и отключение пользователя, только ADMIN |
| GET / POST `/api/hotels` | Список отелей / создание отеля |
| GET / PUT / DELETE `/api/hotels/{id}` | Просмотр, изменение и удаление отеля |
| GET `/api/rooms` | Свободные номера на заданные даты |
| GET `/api/rooms/recommend` | Свободные номера, начиная с наименее часто бронируемых |
| GET `/api/rooms/all` | Все номера, включая ремонт, только ADMIN |
| POST `/api/rooms` | Создаёт номер |
| GET / PUT / DELETE `/api/rooms/{id}` | Просмотр, изменение и удаление номера |
| GET `/api/hotels/statistics` | Статистика занятости, только ADMIN |

Изменять отели и номера может только ADMIN. Просмотр доступен USER и ADMIN. Даже администратор видит через API бронирований только свои брони.

Для свободных номеров нужны параметры `startDate` и `endDate`; дополнительно можно передать `hotelId`. Список отелей поддерживает поиск `q` и сортировку `sort=id|name|address`. Отели, пользователи и история бронирований поддерживают `page` от 0 и `size` от 1 до 100. Статистика принимает даты, необязательный `hotelId` и сортировку `id`, `timesBooked` или `occupancy`.

Для совместимости с заданием оставлены пути `/user/register`, `/user/auth`, `POST /booking`, `GET /bookings`, `GET/DELETE /booking/{id}`, `POST /user` и `PATCH/DELETE /user?id=...`. Полные тела запросов доступны в Swagger.

## Как проходит бронирование

Сначала Booking сохраняет бронь со статусом `PENDING`. Затем просит Hotel занять номер на нужные даты. После успешного ответа статус меняется на `CONFIRMED`. Если Hotel вернул ошибку или не ответил вовремя, бронь становится `CANCELLED`, а Booking отправляет запрос на освобождение номера.

Если освобождение тоже не удалось, остаётся отметка `releasePending`. Фоновая задача повторяет попытку. Внутренние запросы `confirm-availability` и `release` доступны только с технической ролью INTERNAL и закрыты на Gateway.

Даты проверяются по UTC: заезд не должен быть в прошлом, выезд должен быть позже заезда, срок — не больше 366 ночей. День выезда не занят, поэтому следующая бронь может начаться в этот же день. Для переноса дат нужно отменить старую бронь и создать новую.

При автоподборе `roomId` игнорируется. Номера выбираются по `times_booked`, при равенстве — по id. Если другой запрос успел занять первый номер, проверяется следующий. Поле `available` означает, что номер пригоден для заселения; свободные даты проверяются отдельно.

Ошибки возвращаются в общем формате `ErrorDto` с кодом, сообщением, путём запроса и `traceId`. Основные коды: `400` — неверные данные, `401` — проблема с авторизацией по JWT, `403` — нет прав, `404` — ресурс не найден или чужая бронь, `409` — конфликт, `503` — Hotel недоступен, `504` — тайм-аут или ошибка соединения. Заголовок `X-Trace-Id` помогает найти запрос в логах разных сервисов.

## Тесты

Команда `mvnw.cmd clean verify` запускает тесты и проверку стиля. В проекте есть четыре набора:

- `HotelIntegrationTest` — отели, номера, занятость, статистика и параллельные брони.
- `BookingIntegrationTest` — состояния брони, повторы запросов, компенсация, восстановление и права доступа.
- `HttpHotelClientTest` — HTTP-ошибки, тайм-ауты, повторы и Circuit Breaker.
- `GatewaySecurityTest` — проверка JWT и запрет внутренних маршрутов.

MockMvc проверяет API бизнес-сервисов с H2, WebTestClient — Gateway. В тестах HTTP-клиента поднимается локальный сервер, который возвращает ошибки или задерживает ответ. В тестах саги взаимодействие с Hotel заменено моком.
